# التقدم

## المرحلة 1 — الأساس التقني ✅ (checkpoint)
- Backend: Django 5.2 + DRF، إعدادات بيئة، PostgreSQL 17، Argon2.
- الهوية: مستخدم مخصص (بريد مطبّع غير حساس لحالة الأحرف)، JWT مع تدوير وإبطال كامل للجلسات عند الخروج أو تغيير كلمة المرور أو التعطيل، قفل الحساب بعد محاولات فاشلة بشكل ذري (يستمر رغم الخطأ)، MFA/TOTP، تغيير كلمة المرور الذاتي.
- RBAC: سجل صلاحيات `module.resource.action` + أدوار قابلة للتعديل + قوالب الأدوار العشرة.
  - `superuser` لا يتجاوز الصلاحيات؛ مدير النظام بلا `approve/post` تلقائياً ولا يقبل إضافتها (§9).
  - حماية كاملة من تصعيد الصلاحيات (Grant-Ceiling: لا يمنح المستخدم دوراً أو صلاحية لا يملكها، ولا يعدّل أدواره أو حدوده المالية بنفسه، ولا يُعطَّل آخر `SYSTEM_ADMIN`).
- التدقيق: `AuditEvent` غير قابل للتعديل/الحذف في التطبيق **وبمشغّل PostgreSQL**، مع تسجيل فروق القيم قبل/بعد للإعدادات وحدود الموافقات وتسلسل المستندات.
- إعدادات الكيان الواحد + ترقيم المستندات بقفل صف (بلا تعارض) مع التحقق الصارم من قوالب الترقيم (`pattern`).
- أخطاء API موحدة مع `trace_id` مفلتر، حماية `X-Forwarded-For` و Rate Limiting (`NUM_PROXIES`)، ترقيم صفحات، OpenAPI: `/api/docs/`.
- Frontend: Vite + React + TS، PWA (الـ API لا يُخزَّن مؤقتاً)، RTL/LTR حقيقي (عربي افتراضي)، دخول + MFA، قوائم حسب الصلاحية، المستخدمون، سجل التدقيق.
- الاختبارات: 21 backend + 2 frontend ناجحة.

## المرحلة 2 — CRM والكتالوج وقوائم الأسعار ✅ (مكتملة)
- **CRM (`apps/crm`)**:
  - `Customer`: إدارة ملفات العملاء (مستشفيات، مراكز، عيادات، حكومي، موزع) مع ترقيم تلقائي متسلسل للمستندات (`CUST-YYYY-NNNNNN`).
  - `Contact`: جهات اتصال متعددة لكل عميل مع أدوار وظيفية والتبديل الذري لجهة الاتصال الرئيسية (`is_primary`).
  - `Opportunity`: دورة حياة الفرص التجارية (مراحل، قيمة متوقعة، نسبة احتمالية، مصدر)، مع تسجيل تدقيق حساس عند الإغلاق (`WON`/`LOST`).
  - `Activity`: متابعة الزيارات الميدانية، المكالمات، الاجتماعات، والعروض التوضيحية مع مواعيد ونتائج المتابعة.
- **الكتالوج الطبي (`apps/catalog`)**:
  - فصل المنتج (`Product`) عن الموديل والمواصفات الفنية (`ProductModel`) والأصول التسلسلية وفق ADR-034.
  - تصنيف الأجهزة الطبية (`Category`) والشركات المصنعة/الموردين (`Manufacturer` مثل الشريك الصيني).
  - مواصفات فنية ومرفقات واشتراطات التشغيل، مع مسار اعتماد رسمي للموديلات (`catalog.model.approve`).
- **محرك التسعير (`apps/pricing`)**:
  - قوائم أسعار متعددة العملات والتواريخ (`PriceList`) مع عدم الكتابة فوق الأسعار التاريخية.
  - بنود التسعير (`PriceListItem`) مع تحديد سعر البيع المعتمد والحد الأدنى.
  - **حماية حقل تكلفة المورد (`pricing.cost.view`)**: حجب تلقائي لتكلفة المورد وهامش الربح عن موظف المبيعات، وإظهاره فقط للمدراء والمصرح لهم.
- **Frontend**:
  - صفحات كاملة لإدارة العملاء (`Customers.tsx`)، الكتالوج الطبي وموديلاته (`Catalog.tsx`)، وقوائم الأسعار وبنودها (`PriceLists.tsx`).
  - دعم RTL كامل وترجمة عربية/إنجليزية في `i18n.ts`.
- **الاختبارات**:
  - 28 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح) + بناء Vite/PWA نظيف بدون أي أخطاء.

## المرحلة 3 — عروض الأسعار والصفقات وطلبات المورد ✅ (مكتملة)
- **عروض الأسعار (`apps/quotations`)**:
  - `Quotation`: ترقيم آلي (`QT-YYYY-NNNNNN`)، ارتباط بالعميل والفرصة والنموذج التجاري والعملة.
  - `QuotationVersion`: إصدارات غير قابلة للتعديل (`v1`, `v2`, ...)، تجميد كامل للبيانات (`Snapshot` JSON) عند الاعتماد أو الإرسال؛ لا يغير تعديل الكتالوج أو الأسعار أي عرض مرسل.
  - **حوكمة الموافقات والخصومات (ADR-032, §9)**: فحص آلي لسقف خصم المستخدم وسقف قيم الاعتماد، تحويل العرض تلقائياً لحالة `PENDING_APPROVAL` عند التجاوز، ومنع منشئ العرض من اعتماد خصمه بنفسه.
  - حماية بنود العرض المعتمد/المرسل من التعديل أو الحذف (إرجاع خطأ 422 مع اشتراط إنشاء إصدار جديد).
- **الصفقات وأوامر البيع (`apps/sales_orders`)**:
  - `Deal`: حقول إلزامية للنموذج التجاري (`commercial_model`: بيع مباشر `DIRECT_SALE`، وكالة `AGENCY`، مناقصة `TENDER`)، والبائع القانوني (`seller_of_record`)، ومصدر الفاتورة، ومستلم الأموال، ومتابعة عمولة الوكالة.
  - `SalesOrder` & `SalesOrderLine`: أوامر بيع تنفيذية مرتبطة بالصفقة وشروط التسليم والدفع.
  - **التحويل السلس دون إعادة إدخال**: نقطة `/api/v1/deals/from-quotation/` لتحويل العرض المقبول مباشرة إلى صفقة وأمر بيع مع نسخ كامل البنود والأسعار.
- **إدارة الموردين والمشتريات (`apps/procurement`)**:
  - `Supplier`: ملف الشريك/المورد الصيني والموردين الآخرين، العملات، وشروط السداد.
  - `SupplierOrder`: طلبات التوريد للمصنع الصيني (`PO-YYYY-NNNNNN`)، التمييز بين شراء المخزون وتوريد الصفقات وتنسيق الوكالة، وتسجيل وتأكيد رقم الفاتورة المبدئية (`supplier_pi_reference`) وموانئ الشحن والوصول وتكاليف الشحن والتخليص.
- **Frontend**:
  - صفحات كاملة لعروض الأسعار (`Quotations.tsx`)، الصفقات وأوامر البيع (`Deals.tsx`)، والمشتريات (`Procurement.tsx`).
  - مسارات عمل تفاعلية للإرسال، القبول، والتحويل إلى صفقة، مع إشعارات تدقيق حالة الاعتماد.
- **الاختبارات**:
  - 34 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح).

## المرحلة 4 — الشحن والمخزون والأصول متعددة الملكية ✅ (مكتملة)
- **إدارة الشحن واللوجستيات (`apps/shipments`)**:
  - `Shipment`: ربط بأوامر التوريد للمورد الصيني أو أوامر البيع للعملاء (`SHP-YYYY-NNNNNN`).
  - تتبع الموانئ (مثل Shenzhen Port إلى Aden Port)، شركة الملاحة ورقم التتبع، وتكاليف الشحن والتخليص الجمركي.
  - `ShipmentDocument`: أرشفة بوالص الشحن (B/L)، كشوف التعبئة (Packing List)، الفواتير التجارية، وشهادات المنشأ وفحص ما قبل الشحن.
  - `ShipmentEvent`: خط زمني لتتبع المحطات والمراحل اللوجستية حتى الاستلام الفعلي.
- **المخزون والأصول متعددة الملكية (`apps/inventory`)**:
  - **الفصل الحتمي بين الملكية والحيازة والموقع (المبدأ الحاكم، §1.1، §5.8، ADR-023)**:
    - `Location`: مواقع متعددة (مستودع رئيسي، فرع، في العبور والشحن، موقع العميل، ورشة صيانة، أمانة خارجية).
    - `OwnershipRecord`: توثيق المالك القانوني (الشركة المحلية، المورد الصيني، العميل) وفترة الملكية ورقم المستند المثبت لها؛ نقل الجهاز لموقع العميل لا ينقل ملكيته.
    - `CustodyRecord`: توثيق الحائز الفعلي للجهاز (أمين مستودع، مهندس طبي، مستشفى للتجربة) والهدف وتاريخ الاستلام والتسليم.
  - `SerialAsset`: ملف لكل جهاز طبي برقم تسلسلي فريد (`serial_number`)، وتتبع حالته وموقعه وتكلفته الفردية المباشرة (ADR-024).
  - `StockMovement`: سجل حركات مخزنية غير قابلة للتعديل أو الحذف بعد الترحيل (`is_posted`). الرصيد المخزني مشتق كلياً من مجموع الحركات دون أي تعديل يدوي مباشر.
  - `StockCount` & `StockCountItem`: الجرد الدوري الفعلي، حساب الفروقات (عجز/فائض)، والترحيل التلقائي لقيود التسوية المخزنية (`ADJUSTMENT`).
- **Frontend**:
  - صفحة المخزون والأصول ([Inventory.tsx](file:///c:/ziad/smses/frontend/src/pages/Inventory.tsx)): تبويبات للأجهزة التسلسلية مع إبراز فصل المالك القانوني عن الحائز والموقع، وسجل الحركات المخزنية، والمواقع.
  - صفحة الشحن واللوجستيات ([Shipments.tsx](file:///c:/ziad/smses/frontend/src/pages/Shipments.tsx)): متابعة البواخر وأرقام التتبع وموانئ الوصول وسجل المحطات.
- **الاختبارات**:
  - 38 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح).

## المرحلة 5 — المحاسبة المزدوجة، الذمم، الفواتير، الدفعات، البنوك والعملات ✅ (مكتملة)
- **المحاسبة المزدوجة والأستاذ العام (`apps/accounting`)**:
  - `Currency`: إدارة العملات المتعددة (YER الأساسية المحاسبية، USD، CNY، SAR، EUR) وفق المعايير المالية (§8.4).
  - `ExchangeRate`: جدول أسعار الصرف التاريخية المؤرخة وتحديد المصدر (البنك المركزي، السوق، مخصص) مع الحفاظ التام على الأسعار التاريخية.
  - `Account`: دليل الحسابات الشجري (أصول، خصوم، حقوق ملكية، إيرادات، مصروفات)، حسابات تسوية وحسابات فرعية.
  - `JournalEntry` & `JournalLine`: قيود يومية مزدوجة متوازنة (`sum(base_debit) == sum(base_credit)`).
  - **قاعدة الأمان المالي (§8.1، §9، ADR-037)**: لا حذف ولا تعديل للقيود المرحلة على الإطلاق؛ التصحيح يتم حصراً عبر القيد العكسي المرتبط بالأصل (`reverse_journal_entry`).
  - `get_trial_balance`: احتساب ميزان المراجعة الحي الموزون لكل حساب ومجموع الأرصدة.
- **الفواتير والمدفوعات والبنوك (`apps/payments`)**:
  - `BankAccount`: إدارة الحسابات المصرفية والصناديق النقدية بالعملات المختلفة ورصيدها الآني وحسابها في الأستاذ العام.
  - `CustomerInvoice` & `SupplierBill`: فواتير العملاء وفواتير الموردين مع الترحيل التلقائي للقيود المحاسبية المتوازنة في الأستاذ العام وتحديث الذمم المدينة والدائنة.
  - `Payment`: سندات القبض والصرف مع التحديث الذري لرصيد البنك/الصندوق وتوليد القيد المحاسبي.
  - `PaymentAllocation`: توزيع الدفعة الواحدة على عدة فواتير مستحقة جزئياً أو كلياً مع التحقق الصارم من عدم تجاوز الرصيد المتاح.
- **Frontend**:
  - صفحة المحاسبة ([Accounting.tsx](file:///c:/ziad/smses/frontend/src/pages/Accounting.tsx)): تبويبات لقيود اليومية (مع عرض الأسطر والترحيل والعكس)، دليل الحسابات، ميزان المراجعة المتوازن، والعملات وأسعار الصرف.
  - صفحة الفواتير والمدفوعات ([Payments.tsx](file:///c:/ziad/smses/frontend/src/pages/Payments.tsx)): تبويبات لفواتير العملاء، فواتير الموردين، سندات القبض والصرف مع نافذة توزيع المبالغ، والصناديق والحسابات المصرفية.
- **الاختبارات**:
  - 48 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح).

## المرحلة 6 — الهندسة الطبية والتركيب والتشغيل والضمان والصيانة ✅ (مكتملة)
- **الهندسة الطبية والخدمة الفنية (`apps/biomedical`)**:
  - `InstallationProtocol`: محاضر التركيب والتشغيل والتسليم الفني والسريري (`INST-YYYY-NNNNNN`)، اشتراط اجتياز قائمة التحقق الإلزامية (السلامة الكهربائية الطبية، المعايرة والأداء، وتدريب الكادر الطبي) قبل الاعتماد؛ وتحديث حالة الجهاز إلى "مسلّم للعميل" وتوليد عقد الضمان تلقائياً فور الاعتماد.
  - `WarrantyContract`: عقود وسجلات الضمان الطبي (`WAR-YYYY-NNNNNN`) متضمنة ضمان الشركة المصنعة الصينية، وضمان العميل المحلي، وعقود الصيانة الممتدة، ومستوى اتفاقية الخدمة (SLA response hours).
  - `ServiceTicket`: إدارة تذاكر الصيانة والخدمة الفنية (`SRV-YYYY-NNNNNN`) بمختلف الأنواع (وقائية دورية، تصحيحية، عطل طارئ، معايرة) والأولويات ومتابعة تكاليف ساعات العمل والقطع وسير العمليات.
  - `ServiceVisit`: توثيق زيارات المهندسين الميدانية، الفحوصات التشخيصية، الإجراءات الفنية المتخذة، وتوقيع العميل المستلم.
  - `SparePartRequest`: دورة طلب واعتماد قطع الغيار من الشركة الصينية أو المخزون، وتحديد التغطية (مجانياً بالضمان أو على حساب العميل) وتحديث تكلفة التذكرة آلياً.
- **Frontend**:
  - صفحة الهندسة الطبية ([Biomedical.tsx](file:///c:/ziad/smses/frontend/src/pages/Biomedical.tsx)): تبويبات لتذاكر الصيانة (مع تفاصيل الزيارات والقطع وتعيين المهندسين والإغلاق)، محاضر التركيب والتشغيل وقوائم التحقق والاعتماد، عقود الضمان، وطلبات قطع الغيار.
- **الاختبارات**:
  - 51 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح).

## المرحلة 7 — الوثائق والأرشفة، واستخراج البيانات بالذكاء الاصطناعي (AI Gateway)، ونظام الإشعارات ✅ (مكتملة)
- **أرشفة الوثائق والذكاء الاصطناعي (`apps/documents_ai`)**:
  - `Document`: أرشفة وحفظ الوثائق والمستندات الفنية والتجارية (`DOC-YYYY-NNNNNN`)، وتصنيف أنواعها (بوالص شحن B/L، كشوف تعبئة PL، شهادات منشأ، كتالوجات، أدلة تشغيل، فواتير PI، إعلانات جمركية).
  - `ExtractionJob`: مهام الاستخراج الآلي (`EXT-YYYY-NNNNNN`) مع بوابة الذكاء الاصطناعي (`AI Gateway`) وضبط المزود ومستوى الثقة.
  - **قاعدة منع الاختلاق والمراجعة البشرية الإلزامية (§5.12)**: وضع علامة `is_unknown_or_missing` صريحة على الحقول الناقصة، حظر الاعتماد التلقائي، واشتراط المراجعة والتعديل البشري المعتمد (`documents.extraction.approve`) قبل ترحيل البيانات للكتالوج أو التسعير.
  - `ExtractionField`: حقول الاستخراج التفصيلية مع رقم الصفحة والقيمة المستخرجة وقيمة التصحيح ومستوى الثقة.
- **نظام الإشعارات متعدد القنوات (`apps/notifications`)**:
  - `Notification`: إشعارات فورية عبر القنوات (داخل النظام IN_APP، البريد الإلكتروني EMAIL، الرسائل القصيرة SMS، وتطبيق WhatsApp).
  - `NotificationTemplate`: قوالب ديناميكية باللغتين العربية والإنجليزية.
  - `DeliveryAttempt`: سجل تتبع محاولات الإرسال وحالات التسليم وإعادة المحاولة.
  - مركز الإشعارات الفوري في الواجهة: مؤشر الجرس الحي في الشريط الجانبي مع العداد الآني والتحديث والتحديد كمقروء.
- **Frontend**:
  - صفحة الوثائق والذكاء الاصطناعي ([DocumentsAI.tsx](file:///c:/ziad/smses/frontend/src/pages/DocumentsAI.tsx)): إدارة المستندات ومهام الاستخراج ومراجعة واعتماد الحقول المستخرجة.
  - مكوّن الإشعارات الحي ([NotificationCenter.tsx](file:///c:/ziad/smses/frontend/src/components/NotificationCenter.tsx)): جرس إشعارات آني في الواجهة.
- **الاختبارات**:
  - 56 اختبار Backend (100% نجاح) + 2 اختبارات Frontend (100% نجاح).

## المرحلة 8 — التقارير، لوحات التحكم التنفيذية، وتحليلات الأعمال، ومحرك التصدير ✅ (مكتملة)
- **محرك التقارير والتحليلات (`apps/reporting`)**:
  - `DashboardSummaryView` (`/api/v1/reporting/dashboard/`): لوحة مؤشرات قيادية تنفيذية شاملة للمبيعات، الذمم، الشحنات، الأصول، وتذاكر الصيانة.
  - **عزل التكلفة والأرباح (§5.1)**: حجب تلقائي وصارم لبيانات التكلفة وهامش الربح عن مستخدمي المبيعات الذين لا يملكون صلاحية `pricing.cost.view` أو `reporting.financial.view`.
  - `ReceivablesAgingReportView` (`/api/v1/reporting/receivables-aging/`): تقرير أعمار الديون التفصيلي لكل عميل مقسم زمنياً (حالي، 1-30، 31-60، 61-90، و90+ يوماً) مع كشف الفواتير غير المحصلة.
  - `CommercialReportView` (`/api/v1/reporting/commercial/`): مسار الفرص البيعية، معدل الإغلاق والفوز (Win Rate %)، وتوزيع الصفقات حسب النموذج التجاري (بيع مباشر، وكالة، مناقصة)، وأعلى العملاء والموديلات.
  - `WarrantiesForecastReportView` (`/api/v1/reporting/warranties-forecast/`): توقعات انتهاء الضمان الطبي للأجهزة (منتهية، تنتهي خلال 30 يوماً، 60 يوماً، 90 يوماً، ونشطة) وضمان الشركة الصينية المصنعة والعميل.
  - `MaintenancePerformanceReportView` (`/api/v1/reporting/maintenance-performance/`): مؤشرات أداء الهندسة الطبية (نسبة حل التذاكر، التوزيع حسب النوع والأولوية، وأداء المهندسين الطبيين).
